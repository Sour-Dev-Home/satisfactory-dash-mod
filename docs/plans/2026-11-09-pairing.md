# Device-code pairing (mod 0.3.0) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or
> superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A fresh install with no cfg file pairs with the dashboard from a code shown in the server console (and in chat
when one player is online), with no file edit.

**Architecture:**
- A pure-logic unit `FPairing` (SatisDashCore, no engine types) runs the window, the start and poll schedule, and the
  replies. `FAgent` owns it and adds the state `Pairing`.
- `FDriver` sends its requests through the existing `ITransport`, and feeds it the player count and the server name
  through three new `IGameReader` methods, which `FGameReader` implements with FactoryGame headers.
- The harness gets a loopback cfg before every boot, a pairing approval on the backend host, and a new `pair` core run.

**Tech Stack:** UE 5.6.1 C++ / SML 3.12.0 (mod and automation tests); TypeScript, Vitest and zod (harness).

**Spec:** `docs/specs/2026-11-09-pairing-design.md`. Read it first; it is the authority. The contract is satisfactory-dash
`packages/shared/src/pairing.ts`.

## Global Constraints

- Repo rules (`CLAUDE.md`):
  - every new SML, FactoryGame or UE symbol, include or module gets an `api-sources.md` row with `path:line` from the
    pinned headers (`D:\SatisfactoryModding\SatisfactoryModLoader\Source\...`), and `npm run harness -- check-api` must
    pass;
  - never weaken a `runs/*/pass.ts` condition;
  - evidence is machine-written;
  - spikes and runs talk to loopback only;
  - no PII or local user-profile paths in anything committed.
- Contract values, verbatim from `pairing.ts`:
  - `PAIRING_EXPIRES_IN_SECONDS = 900`, `PAIRING_POLL_INTERVAL_SECONDS = 5`, `PAIRING_SLOW_DOWN_SECONDS = 5`;
  - statuses `pending | expired | slow_down | approved`;
  - `pairingSecret` matches `/^[A-Za-z0-9_-]{22}$/`;
  - `userCode` is the enrolment-code shape (`IsEnrollmentCode`);
  - `serverName`: 1 to 200 characters, none in `\p{C}\p{Zl}\p{Zp}`;
  - `agentVersion`: 1 to 32 characters, `[0-9A-Za-z.+/-]` (after dash #871);
  - `approvedBy`: optional, 1 to 64 characters.
- The pairing window lasts 3600 s, and at most one window opens per rolling 3600 s.
- The console line, verbatim: `Pairing code <CODE>: sign in at https://satis-manager.com/pair and enter it (expires in <N> minutes)`.
  For a non-default backend, the URL part reads `on your dashboard's Pair page`, giving
  `Pairing code <CODE>: sign in on your dashboard's Pair page and enter it (expires in <N> minutes)`.
- Window closed: `No pairing code active: join the server or restart it to get a new one`.
- Paired: `Paired with the dashboard; reporting to the backend`, plus ` (approved by "<name>")` when present.
- Halt line (`Agent.cpp:245`): `The backend rejected the credential (401): this server was revoked in the dashboard. Stopped; restart the server to pair it again, or add a code to SatisDashAgent.cfg`.
- 429 on start: `Waiting <n> s for a pairing code (the backend's per-address limit)` (Display, once per wait).
- 400 on start: `The backend refused the pairing request (400); retrying in an hour` (Warning, once).
- `pairingSecret` never in a log line, a URL, a header or on disk.
- The cfg code always wins over pairing. A credential for another backend stays `Idle`.
- Chat goes only through `AFGChatManager::BroadcastChatMessage`, only when exactly 1 player is connected.
- Subagents use Sonnet. No local UE build while a runner job runs. Mod builds and tests run on the runner (`mod-test`,
  `linux-build`).
- **Ruling (plan):** 429 waits reuse `ParseRetryAfterSeconds` (`Pusher.h:17`, capped at 300 s). The spec's "capped at 1
  hour" is an upper bound; a shorter cap only retries sooner, and a refused start isn't counted. If wrong, it costs a few
  extra 429s an hour.

## Review Focus

1. **A cfg with no code at all** (the default the mod writes at `Boot`, `Agent.h:20`) must pair. It must not stay
   `Idle`. Pinned by Task 4's boot test.
2. **A pairing secret must never reach a log.** That includes the warning paths: 400, a 201 not in form, unknown statuses.
   Pinned by Task 3's log-capture test and Task 8's pass rule.
3. **Restarts and the window.** A restart during an open pairing must not leave two pairings polling. The driver must
   never have two pairing requests in flight. Pinned by Task 5's "one in flight" test.
4. **A cfg edit adding a code while a poll is in flight** must not end up enrolled *and* paired. The poll's reply arriving
   after the switch is ignored. Pinned by Task 4's "code wins mid-poll" test.
5. **A player count the game can't read (-1)** must not trigger chat or reopen a window. Pinned by Task 3's
   `ShouldPostCode` and `OnPlayers` tests.

**Behaviour, which the tests pin.** Times are in seconds, and Random01 is fixed at 1.0 in tests, so `BackoffSeconds(n, 1.0)`
is deterministic. Read `Pusher.cpp` for its values; don't assume them.
- **`Open(Now)`:** if `Now - WindowOpenedAt < 3600` and not stopped, it does nothing. Otherwise:
  - `WindowOpenedAt = Now`, `WindowEndsAt = Now + 3600`, `bStopped = false`, `NextAt = Now`;
  - clear the code, `Failures = 0`, `bClosedLogged = false`.
  - **Restarts:** a fresh `FPairing` has `WindowOpenedAt = -1e18`, so it opens.
- **`Next`:** unset if stopped, in flight, `Now < NextAt` or the window is closed.
  - If the window closed and there's no open code, log the closed line once (`bClosedLogged`) and return unset.
  - If there's a code and `Now < CodeExpiresAt`: a poll (`BuildPairingPollRequest(Config, Secret)`).
  - Otherwise: a start, with `bSendName ? CleanServerName(ServerName()) : ""`.
  - Remember `LastConfig = Config`, set `bInFlight`.
- **`Finish`:**
  - unset unless in flight;
  - clear `bInFlight`, then go by the §3 table:
    - **start 201 parsed:**
      - adopt the secret, code, `CodeExpiresAt = Now + ExpiresIn` and `IntervalSeconds`;
      - `Failures = 0`, `bSendName = true`, `NextAt = Now + Interval`;
      - log `PairingCodeLine` (Display);
      - `PendingChat = line` if `ShouldPostCode(PlayersNow, true, false)`.
    - **start 400:** if a name was sent, set `bSendName = false` and `NextAt = Now`. Otherwise warn once and
      `NextAt = Now + 3600`.
    - **start 429:** `NextAt = Now + max(ParseRetryAfterSeconds(...).Get(60), 1)`, and log the waiting line (Display).
    - **start other, or a 201 not in form:** `NextAt = Now + BackoffSeconds(Failures++, r)`.
    - **poll Pending:** `NextAt = Now + Interval`.
    - **poll SlowDown:** `Interval += 5`, then the same.
    - **poll Expired, or 400:** clear the code; `NextAt = Now`, so the next `Next` starts a new one if the window is
      open.
    - **poll 429:** Retry-After as for a start.
    - **poll unset, 5xx or 0:** `BackoffSeconds`. The code is kept until `CodeExpiresAt`.
    - **poll Approved:** return it, and `Stop()`.
- **`OnPlayers(P, Now)`:**
  - if `P == 1 && LastPlayers == 0` (a join to 1; `LastPlayers` starts at -1, so the first reading never counts as a
    join), then:
    - with the window closed, call `Open(Now)`; the new code then chats via `ShouldPostCode` when it arrives;
    - with an open code, `PendingChat = PairingCodeLine(...)` with the remaining minutes.
  - Then `LastPlayers = P` and `PlayersNow = P`. A `P < 0` changes nothing.
  - `Open` is subject to its one-per-hour rule.
- **`ShouldPostCode(P, bNew, bJoined)`** = `P == 1 && (bNew || bJoined)`.
- **`PairingCodeLine`:**
  - minutes = `FMath::Max(1, ExpiresIn / 60)`;
  - the URL part depends on `Config.BackendUrl == DefaultBackendUrl` (exact match).
- **The closed line** is logged when `Next` first finds the window closed with no code. It's logged again only after a new
  `Open`.
